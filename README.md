# gcode-lint

[![CI](https://github.com/keivanmalhani/gcode-lint/actions/workflows/ci.yml/badge.svg)](https://github.com/keivanmalhani/gcode-lint/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

Static analysis for sliced 3D printer gcode. It reads the file once and tells
you what is going to go wrong before you start a twelve hour print.

## What it does

`gcode-lint` streams a sliced `.gcode` file, reconstructs the machine state
line by line, and checks that state against twelve rules. Each finding carries
a severity, the line number, what is wrong, why it matters, and how to fix it.

It reads the header comments that PrusaSlicer, Cura, OrcaSlicer and Bambu
Studio write, so it knows which slicer produced the file, which material the
file was sliced for, and what the slicer thought the print would cost in time
and filament. It compares those claims against what the file actually contains.

## Why it exists

A long print fails in the first ninety seconds and you find out eleven hours
later. Most of those failures are already visible in the file: a first layer
running too fast to stick, ABS with the part cooling fan on, a nozzle
temperature left over from the last filament, a model hanging off the front of
the plate, a spool with less on it than the print needs. The slicer does not
warn you, because it does not know which machine the file is going to or how
much filament is on the spool.

The checks are the product. Everything else is plumbing.

## Install

Python 3.11 or newer, standard library only, no dependencies.

```
git clone https://github.com/keivanmalhani/gcode-lint
cd gcode-lint
pip install -e .
```

## Use

```
gcode-lint check part.gcode --printer bambu-p1s
gcode-lint check part.gcode --bed 250x210x220
gcode-lint check part.gcode --printer prusa-mk4 --remaining 240g
gcode-lint check part.gcode --printer ender3 --stats
gcode-lint check part.gcode --json --fail-on high
gcode-lint rules
gcode-lint --version
```

| option | meaning |
| --- | --- |
| `--printer NAME` | build volume from a shipped preset |
| `--bed WxHxD` | build volume in mm for anything else, X by Y by Z |
| `--remaining MASS` | filament left on the spool, `240g` or `1.2kg` |
| `--json` | the whole report as JSON, including per layer stats with `--stats` |
| `--fail-on high\|medium\|low` | lowest severity that exits 1, default `medium` |
| `--stats` | layer by layer time, filament and maximum speed |
| `--first-layer-speed MM_S` | rule 1 threshold, default 40 |
| `--travel-threshold MM` | rule 4 threshold, default 3 |
| `--diameter MM` | filament diameter for mass estimates, default 1.75 |

Exit codes:

| code | meaning |
| --- | --- |
| 0 | nothing at or above the `--fail-on` level |
| 1 | findings at or above the `--fail-on` level |
| 2 | the file could not be parsed |

If you do not pass `--printer` or `--bed`, the printer model in the slicer
header is matched against the presets. When nothing matches, the build volume
check is skipped and the report says so rather than passing silently.

## The rules

| # | rule | severity | what it looks for |
| --- | --- | --- | --- |
| 1 | `first-layer-speed` | medium, high past 1.5x | Extrusion moves on layer one above the speed threshold. Adhesion failures start here. |
| 2 | `bed-adhesion` | medium | No skirt, brim, raft or purge line runs before the first extrusion of the model. |
| 3 | `temperature-range` | high nozzle, medium bed | `M104`/`M109`/`M140`/`M190` targets outside the window for the material the header declares. PLA above 235 C, PETG below 220 C, ABS below 230 C, and so on for fifteen materials. |
| 4 | `travel-retraction` | medium, high when frequent | A travel longer than the threshold that starts with the filament still under pressure. This is what stringing is. |
| 5 | `z-hop` | medium, high when frequent | A travel that crosses material already laid down on the same layer without lifting z. |
| 6 | `first-layer-fan` | medium, high above 50 percent | Part cooling running on layer one for a material that needs it off: ABS, ASA, PC, PA, HIPS, PPS, PEEK, PEI. |
| 7 | `cold-extrusion` | high, medium if only the wait is missing | An extrusion move before the hotend has a target, or before any `M109` has blocked for it. |
| 8 | `build-volume` | high, low for an end gcode park | Any X, Y or Z coordinate outside the printer volume, or below the origin. |
| 9 | `end-retraction` | medium, low if it retracts too late | The end gcode parks without retracting, so the melt zone drains onto the finished part. |
| 10 | `chamber` | medium, low on an enclosed printer | No `M141`/`M191` and no chamber temperature in the header, for a material that wants one. |
| 11 | `filament-remaining` | high, low on a thin margin | What the print needs against what `--remaining` says is on the spool, with the layer it runs out at. |
| 12 | `header-consistency` | medium | The slicer header filament total against the extrusion the file actually contains, flagged past 10 percent. A stale header means the print time is stale too. |

Rules 11 and 12 work together: when the header total disagrees with the file,
rule 11 stops trusting the header and measures the file instead, and says so.

Run `gcode-lint rules` for the same table on the terminal.

## Printer presets

| `--printer` | machine | build volume | enclosure |
| --- | --- | --- | --- |
| `bambu-a1` | Bambu Lab A1 | 256 x 256 x 256 mm | open |
| `bambu-p1s` | Bambu Lab P1S | 256 x 256 x 256 mm | passive |
| `bambu-x1c` | Bambu Lab X1 Carbon | 256 x 256 x 256 mm | passive |
| `prusa-mk4` | Prusa MK4 | 250 x 210 x 220 mm | open |
| `ender3` | Creality Ender 3 | 220 x 220 x 250 mm | open |

Short names work too: `a1`, `p1s`, `x1c`, `x1 carbon`, `mk4`, `ender 3`.
Anything else goes in as `--bed 350x350x300`.

The enclosure column is not decoration. Rule 10 lowers ABS with no chamber
temperature from medium to low on a P1S or X1C, because the machine holds heat
even though it cannot command a chamber temperature.

## What it will not do

* **It does not simulate the print.** There is no motion planner, no
  acceleration model and no thermal model. The time in `--stats` is the sum of
  distance over feedrate, so it reads low against the slicer estimate, which
  does model acceleration. Treat it as a shape, not a number.
* **It cannot catch a model that is simply badly designed.** Unsupported
  overhangs, walls thinner than the nozzle, a bolt hole that will print
  undersized, a part with no fillet where it needs one: all of that is decided
  upstream of the gcode and is invisible in the file.
* **It does not know your machine.** Whether the plate is clean, whether the
  nozzle is worn, whether the belts are tight, whether the filament has been
  sitting open for a month. It reads a file and nothing else.
* **It does not do collision detection.** A gantry hitting a tall printed part
  or a purge that lands on yesterday's print is out of scope.
* **Crossing detection is an approximation.** Rule 5 keeps a 4 mm occupancy
  grid of the current layer only, so it can miss a travel that clips a corner
  and it says nothing about travels over earlier layers.
* **Arc moves are measured by their chord.** `G2` and `G3` contribute slightly
  short distances to the totals.
* **Everything about the material comes from the header.** A file sliced with
  the wrong filament profile selected is consistent with itself, and the
  temperature and chamber rules will happily agree with it.
* **It never writes to your gcode.** It only reads.

## Development

```
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
pytest -q
```

The tests generate the gcode they need, including a file of more than half a
million lines used to prove that the parser streams. Nothing large is committed.

The parser and the rule engine are separate on purpose. `parser.py` produces a
`ParseResult` of exact aggregates plus bounded evidence lists; every rule in
`rules.py` is a pure function of `(ParseResult, LintConfig)` returning a list of
findings, so a test can hand a rule a state built by hand and assert on what
comes back. Nothing in `rules.py` reads a file.
